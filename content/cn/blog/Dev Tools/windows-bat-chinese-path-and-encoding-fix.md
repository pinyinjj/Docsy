## 1. 运行故障现象与现场特征

在 Windows 系统中通过批处理脚本（.bat）调度跨平台工具链（如 WSL 2, Bash 或 Python）时，若脚本所在路径包含中文字符，子进程常因路径解析失效而中断执行。

典型控制台报错如下：

```text
Starting PX4 SITL simulation in Ubuntu-22.04...
bash: /mnt/c/workspace/4.ROS2 鏈哄櫒浜哄紑鍙戝疄鎴?assets/run_rflysim_px4_session.sh: No such file or directory
[ERROR] PX4 SITL startup failed with exit code 127.
```

该类故障呈现出两个相互关联的特征：

1. 路径中原有的中文字符串 `机器人开发实战` 被转换为乱码 `鏈哄櫒浜哄紑鍙戝疄鎴`。
2. 目录之间的 Windows 路径分隔符 `\`（反斜杠）在乱码之后丢失，导致父级目录名与子级目录名 `assets` 错误拼合为一个不存在的路径节点。

## 2. 字符集编码与路径分隔符吞噬机理

> 代码页（Code Page）是操作系统用于定义字符与字节编码映射关系的数值标识。简体中文 Windows 系统的命令提示符默认使用代码页 936（GBK 编码，双字节字符集）；跨平台运行环境（如 Linux 内核与 WSL 2）通常默认使用代码页 65001（UTF-8 编码，变长多字节字符集）。

### 2.1 字节切分错位

通用文本编辑器通常默认以 UTF-8 编码保存批处理文件。在 UTF-8 编码规范中，标准汉字各占用 3 个字节；而 Windows 命令提示符在解析批处理脚本时，默认按照代码页 936 规则进行双字节切分。

以包含 7 个汉字的短语 `机器人开发实战` 为例，其 UTF-8 原始编码由 21 个十六进制字节组成：

```text
机: E6 9C BA
器: E5 99 A8
人: E4 BA BA
开: E5 BC 80
发: E5 8F 91
实: E5 AE 9E
战: E6 88 98
```

当 Windows 命令提示符按照代码页 936 的双字节规则读取该连续字节流时，前 20 个字节被两两配对成 10 个字符：

| 字节配对 | 对应代码页 936 字符 | Unicode 码点 | 状态说明 |
| :--- | :--- | :--- | :--- |
| `E6 9C` | 鏈 | `U+93C8` | 错位字符 |
| `BA E5` | 哄 | `U+54C4` | 错位字符 |
| `99 A8` | 櫒 | `U+6AD2` | 错位字符 |
| `E4 BA` | 浜 | `U+6D5C` | 错位字符 |
| `BA E5` | 哄 | `U+54C4` | 错位字符 |
| `BC 80` | 紑 | `U+7D11` | 错位字符 |
| `E5 8F` | 鍙 | `U+9359` | 错位字符 |
| `91 E5` | 戝 | `U+621D` | 错位字符 |
| `AE 9E` | 疄 | `U+7584` | 错位字符 |
| `E6 88` | 鎴 | `U+93B4` | 错位字符 |

解析结果即为控制台显示的乱码字符串 `鏈哄櫒浜哄紑鍙戝疄鎴`。

### 2.2 路径分隔符丢失原因

经过前 20 个字节的两两切分后，汉字 `战` 的最后一个字节 `0x98` 被单独残留。在路径字符串中，紧随该汉字之后的是 Windows 路径分隔符 `\`，其 ASCII 码值为 `0x5C`。

在代码页 936 编码体系中：

1. 双字节高位字节（首字节）的合法取值范围为 `0x81 ~ 0xFE`。
2. 双字节低位字节（尾字节）的合法取值范围为 `0x40 ~ 0xFE`（除 `0x7F` 外）。

字节 `0x98` 恰好位于高位字节区间内，而紧随其后的反斜杠字符 `0x5C` 正好落在合法低位字节区间内。命令解释器将 `0x98 0x5C` 整体识别为单一双字节字符，导致反斜杠从语法结构中消失，目录层级边界被抹除。合并后的字符因缺少完整字体支持或解析异常显示为 `?`，使原本独立的 `assets` 目录变为无效路径片段。

## 3. 行尾换行符机制

在涉及 Windows 与 Linux/WSL 2 的混合工作流中，除字符集编码外，行尾控制字符不一致同样会导致子进程中断。

> 行尾换行符（Line Endings）是用于在纯文本中标记单行结束的控制字符序列。Windows 体系使用回车符与换行符组合（CRLF），Linux 与 Unix 体系使用单换行符（LF）。

### 3.1 跨平台行尾定义

| 标识符 | 英文全称 | ASCII 十六进制 | 转义序列 | 目标运行平台 |
| :--- | :--- | :--- | :--- | :--- |
| **LF** | Line Feed | `0x0A` | `\n` | Linux, Unix, macOS, WSL 2 |
| **CRLF** | Carriage Return + Line Feed | `0x0D 0x0A` | `\r\n` | Windows 批处理, 命令提示符 |

### 3.2 换行符不匹配引发的次生错误

换行符在跨系统调用时会产生以下两类典型错误：

1. **Linux 环境解释器失效**：如果被调用的 Shell 脚本（如 `.sh` 文件）在 Windows 编辑器中被保存为 CRLF 格式，Linux 内核在读取脚本首行 Shebang 时，会将多余的回车符 `\r`（ASCII `0x0D`）解析为解释器路径的一部分，触发以下错误：
   ```text
   bash: ./run_rflysim_px4_session.sh: /bin/bash^M: bad interpreter: No such file or directory
   ```
2. **命令参数包含隐藏字符**：脚本中定义或输出的变量若末尾附带 `\r`，在后续字符串拼接时会破坏目标路径或命令参数，导致文件检索失败。
3. **Windows 批处理语法块断裂**：Windows 批处理解析多行复合逻辑块（如 `if (...) else (...)` 或 `for /f (...)`）时，对 CRLF 的行边界具有特定依赖。若将批处理文件保存为单一 LF 换行，部分版本的解释器可能发生括号语法错误。

## 4. 修复方案与工程实施

针对上述两类编码问题，应分别在编码格式, 路径调用方式和换行符三个维度进行标准化处理。

### 4.1 批处理脚本编码转换

将批处理脚本保存为 ANSI 编码是避免 0x5C 吞噬现象的直接方案：

1. 在 VS Code 中打开目标批处理文件（如 `.bat` 文件）。
2. 点击右下角状态栏的编码指示区域（通常显示为 `UTF-8`）。
3. 在上方命令面板中选择 `Save with Encoding` 操作。
4. 检索并选中 `Simplified Chinese (GBK)`。
5. 检查右下角换行符模式，确认保持为 `CRLF`。

### 4.2 统一声明代码页与带签名编码

若项目仓库强制要求所有代码文本统一采用 UTF-8 编码，必须满足以下两项配套配置：

1. 在批处理脚本第一行显式切换终端运行代码页：
   ```bat
   @echo off
   chcp 65001 >nul
   ```
2. 将文件保存为 **UTF-8 with BOM**（包含字节序标记 `EF BB BF`）。该签名有助于 Windows 解释器在初次载入阶段将文件按 Unicode 规则读取。

### 4.3 规避跨环境绝对路径拼接

在批处理中启动 WSL 2 进程时，应避免在 Windows 终端环境下通过字符串拼接传递包含中文字符的绝对路径，改用 WSL 2 提供的切换工作目录参数：

```bat
wsl -d %WSL_DISTRO% --cd "%~dp0" -- bash ./run_rflysim_px4_session.sh
```

该方式由 WSL 2 运行时完成宿主路径到 Linux 挂载路径的映射转换，并在目标目录下以相对路径执行脚本，避免跨进程管道中传递可能被转码的路径字符串。

### 4.4 行尾换行符转换工具

针对从 Windows 环境迁入或被误保存为 CRLF 的 Linux Shell 脚本，可使用格式转换工具进行修正：

```bash
dos2unix run_rflysim_px4_session.sh
```

或使用流编辑器剔除行末的回车符：

```bash
sed -i 's/\r$//' run_rflysim_px4_session.sh
```

同时，在项目根目录的 `.gitattributes` 配置文件中固化换行规则，避免 Git 检出时自动转换：

```gitattributes
*.bat text eol=crlf
*.cmd text eol=crlf
*.sh text eol=lf
*.py text eol=lf
```

## 5. 跨环境兼容性速查表

| 检查维度 | 故障现象 | 根因分类 | 标准修复动作 |
| :--- | :--- | :--- | :--- |
| **字符乱码** | 路径中出现 `鏈哄櫒浜哄紑鍙戝疄鎴` | 字符集切分错位 | 将批处理文件保存为 `GBK` 或 `UTF-8 with BOM` |
| **分隔符缺失** | 路径中的反斜杠被识别为不可见字符或 `?` | 0x5C 双字节吞噬 | 转换脚本编码，避免中文字符尾字节与 `0x5C` 合并 |
| **解释器异常** | 终端提示 `/bin/bash^M: bad interpreter` | 换行符不匹配 | 使用 `dos2unix` 将脚本行尾切换为 `LF` 格式 |
| **子进程退出** | 执行外部脚本返回 `exit code 127` | 路径失效或参数污染 | 改用 `wsl --cd "%~dp0"` 模式并修复行尾换行符 |
